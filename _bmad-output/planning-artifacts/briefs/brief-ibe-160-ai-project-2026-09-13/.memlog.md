- (decision) Idea originates from Niklas's personal consulting experience, not a hypothetical.
- (decision) Scope for course project: a trial/prototype NOT yet connected to the live Tripletex API; integration will be mocked/simulated for this phase, with real API as a future step.
- (decision) Architecture: per-person AI -- each consultant gets their own personal AI agent instance, not one shared org-level agent.
- (decision) Invoicing target: 80% is the org-wide default, but each consultant can have their own configured target overriding the default.
- (decision) Capacity model: standard workday is 7.5h, Mon-Fri; 80% target is measured as a YEARLY goal (not weekly), so it can shift week to week, especially early in the year.
- (decision) UI principle: minimize typing for consultants -- future work is captured via selectable options (client/project, expected hours per day) rather than free text; AI surfaces hints when there is room to reach the target rate.
- (decision) Two dashboard views: consultants see a personal dashboard; leaders see a team/aggregate dashboard.
- (event) Web research on Tripletex API: REST API 2.0 documented at developer.tripletex.no, free self-serve test sandbox (no partner approval needed for single-company use), consumer+employee token auth, rate limit 100req/5s, plausible endpoints for timesheets/projects/budgets/invoices, and an existing OSS precedent (tripletex-mcp) exposing similar data to AI assistants.
- (event) Fast-path draft of brief.md written; assumptions tagged for notification channel and course-deliverable success definition; awaiting user review.
